## 1. What this repository is

An Expo / React Native mobile app for iOS and Android that connects directly to a Nextcloud
server over CalDAV and Nextcloud OCS. There is **no PHP backend in this repository** and no
server-side Nextcloud Calendar app code. The Nextcloud server is external.

Main capabilities:

- Multiple Nextcloud accounts with app-password auth, QR login, TLS trust, and cleartext consent.
- Month, week, 3-day, day, and agenda calendar views.
- Event create/edit/delete, recurrence (this / this-and-following / all), attendees, alarms.
- Nextcloud Talk room creation per event.
- Local-first offline storage and incremental CalDAV sync.
- Home-screen widgets (iOS + Android), iOS Live Activities, local notifications.
- Background sync and widget refresh.

## 4. Architecture and data flow

### Boot and routing

1. `index.ts` imports `expo-router/entry` and registers the Android widget task handler.
2. `app/_layout.tsx` installs `Providers` (Gesture Handler root, WatermelonDB provider, theme),
   runs app initialization, capabilities sync, language sync, orientation lock, widget sync,
   event alerts, and contact cache.
3. `useAppInitialization` migrates legacy AsyncStorage data, rehydrates Zustand stores, initializes
   the database, loads accounts from SecureStore, then syncs calendars and server capabilities.
4. `RootNavigator` renders an Expo Router stack. `app/index.tsx` redirects to `(auth)/setup` when no
   account exists, otherwise to `(tabs)/calendar`.

### Read path

CalDAV response → `src/services/nextcloud/caldav.ts` → iCalendar parsing in
`src/utils/caldav-parse.ts` → WatermelonDB rows via `src/database/sync.ts` → reactive queries
(`useEvents`, `useCalendars`) → normalization/visibility filtering → calendar views.

### Write path

Event form → `src/features/event/hooks/useMutateEvent.ts` → optimistic local write in
`src/database/eventWrites.ts` → CalDAV `PUT`/`PATCH`/`DELETE`/`MOVE` → reconcile or roll back.
Recurring edits support `this`, `thisAndFollowing`, and `all` scopes, including overrides and
EXDATE handling.

### Sync model

- `syncCalendars()` discovers calendars and deletes server-removed calendars plus orphaned events.
- `syncVisibleRange()` fetches the visible range; `syncCalendarDelta()` uses each calendar's
  `sync_token` and ctag, with a full-range fallback when the token resets or the horizon moves.
- A local-write epoch prevents in-flight syncs from clobbering optimistic edits.
- Background sync refreshes a 7-day window, widgets, and notifications via the
  `widget-agenda-refresh` task.
- WatermelonDB is the UI source of truth; the app is local-first.

### Storage and networking

- Accounts and app passwords are stored in SecureStore (`src/services/nextcloud/auth.ts`).
- Non-secret state is in MMKV-backed Zustand stores; `src/stores/legacyStorage.ts` migrates the
  legacy `app-store` blob.
- `trustedFetch` routes requests through the native `tls-trust` module, supports certificate pins
  and explicit trust, blocks unconsented cleartext HTTP, and retries transient failures.
- Never log, commit, or paste app passwords, tokens, keystores, or `.env` values.

### Calendar, event, widget, and native details

- Calendar views: `src/features/calendar/components`, `hooks`, and `utils`. View modes are
  `month`, `week`, `3days`, `day`, `schedule`; constants live in `src/features/calendar/constants.ts`.
- Event editing: `src/features/event` (form, recurrence picker, attendees, alerts, Talk toggle).
- Widgets: iOS `expo-widgets` + Live Activities; Android `react-native-android-widget`; snapshots
  and theme logic live in `src/features/widget`.
- Local modules: `live-updates` (iOS Live Activities), `tls-trust` (TLS/cert handling),
  `zxing-scanner` (QR login).

## 5. Conventions

- Import app code through `@/` (maps to `src/`). Keep relative imports only within a local folder.
- Reuse `src/ui/components` and `src/theme.ts`; do not create a parallel design system.
- Use `lucide-react-native` icons.
- TypeScript is strict: avoid `any`, prefer types from `src/types/index.ts`.
- Match the file's existing indentation and style (the codebase mixes 2- and 4-space blocks).
- Every user-visible string must be added to all locales in `src/locales/*.json`;
  `__tests__/i18n/parity.test.ts` enforces key parity.
- Unit/component tests live in `__tests__/`, grouped by area. Shared mocks live in `__mocks__/`
  and `jest.setup.js`. Theme-dependent components need `ThemeWrapper` from
  `__tests__/helpers/theme.tsx`.
- E2E suites and Maestro flows belong in `e2e/` only.
- Do not edit `android/` or `ios/` by hand. They are generated by `expo prebuild`; change
  `app.config.ts`, a config plugin, or a local native module instead.
- Do not commit generated native projects, build outputs, keystores, secrets, or `.env` files.
  The only tracked file under the root `android/` tree is
  `android/app/src/main/AndroidManifest.xml`; local module sources under `modules/` are tracked
  intentionally.
- Commits use Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`).
- `app.config.ts` enforces `versionCode === major * 10000 + minor * 100 + patch`. Bump
  `package.json` and `versionCode` together.

## 6. Commands

### Isolated local toolchain (mise)

The repository pins its project runtime in `.mise.toml`: **Node 24.22.2** (current LTS, matching
CI's `lts/*` policy) and a non-interactive Corepack prompt. Mise installs under
`~/.local/share/mise` and does **not** touch system Node, OpenCode's runtime, or its plugins.

```bash
mise trust
mise install
mise exec -- node --version        # v24.22.2
mise exec -- corepack --version    # 0.36.0
mise exec -- corepack yarn --version   # 4.5.3
mise exec -- corepack enable       # optional: creates yarn shims only inside the mise Node install
```

Use `mise exec --` for every command (or activate mise in your shell). Do not run
`mise use -g`, `corepack enable` globally, or install a system Node. The repository vendors
Yarn 4.5.3 at `.yarn/releases/yarn-4.5.3.cjs`; `corepack yarn` honors `packageManager` and
`.yarnrc.yml`.

### Prerequisites

Node.js LTS, Corepack, Yarn 4.5.3, JDK 17, Android SDK; Xcode/CocoaPods on macOS for iOS. E2E
additionally needs Docker, an Android emulator, `adb`, Maestro, and `just`. The bootstrap host
initially had no Node/Yarn/adb/Maestro; the isolated mise toolchain and baseline checks were added
later on 2026-10-31 (see `PLAND.md`). Prefix commands with `mise exec --` unless mise is activated.

```bash
# Install (postinstall applies patch-package patches)
mise exec -- corepack yarn install --immutable      # CI
mise exec -- corepack yarn install                  # local development

# Static checks / unit tests
mise exec -- corepack yarn tsc --noEmit
mise exec -- corepack yarn test                     # Jest
mise exec -- corepack yarn jest __tests__/utils/ics.test.ts
mise exec -- corepack yarn jest -t 'RecurrencePicker'

# Development
mise exec -- corepack yarn start                    # Metro
mise exec -- corepack yarn android                  # expo run:android
mise exec -- corepack yarn ios                      # expo run:ios (macOS)
mise exec -- npx expo prebuild                      # generate native projects
mise exec -- npx expo prebuild --clean              # regenerate; deletes android/ and ios/
```

E2E and seeding:

```bash
mise exec -- just e2e-all                  # boot emulator if needed, build APK, run Jest + Maestro
mise exec -- just e2e-build                # prebuild Android + assembleRelease for the booted ABI
mise exec -- just e2e                      # all Jest E2E suites
mise exec -- just e2e e2e/event.e2e.ts     # one suite
mise exec -- just seed                     # seed a Nextcloud instance
mise exec -- just unseed                   # wipe seeded calendars
```

Release: `yarn release` (release-it). CI release is triggered by merging a PR whose title contains
`[release]` into `main`.

## 7. CI/CD and repository settings

| Workflow | Trigger | Purpose | Requirements |
| --- | --- | --- | --- |
| `test.yml` | `pull_request` | `yarn install --immutable`, `tsc --noEmit`, `jest --ci`, Android JS bundle export | Node LTS, Yarn cache |
| `ios-build.yml` | PRs touching app/native paths + `workflow_dispatch` | Expo prebuild, CocoaPods, Xcode simulator build, artifact upload | macOS runner; no Apple signing secrets |
| `security.yml` | PR + push to `main` | Trivy dependency scan, Gitleaks secret scan | `GITLEAKS_LICENSE` secret |
| `plumber.yml` | PR + push to `main` | Plumber score/pipeline checks | Plumber access, OIDC |
| `release.yml` | `workflow_dispatch`; closed PR to `main` with `[release]` | Version bump, changelog, release, EAS dispatch | `APP_ID` variable, `APP_PRIVATE_KEY`, `EXPO_TOKEN` |
| `expo.yml` | `workflow_call` | EAS build and store submission | `EXPO_TOKEN`, EAS project access |

GitHub Actions is enabled on the custom repository and all six workflows are active (the five
inherited workflows plus `ios-build.yml`). The custom repository does **not** yet have upstream
secrets/variables (`APP_ID`, `APP_PRIVATE_KEY`, `EXPO_TOKEN`, `GITLEAKS_LICENSE`) or the upstream
Expo/EAS organization. Do not trigger release/EAS workflows until those are configured or the
workflows are intentionally adapted.

The iOS simulator build is a cold native build and takes roughly 33 minutes on `macos-15`;
macOS arm64 runners can also queue for capacity. Add caching or a larger runner before making it
a required check on every PR.

`main` is **protected**: pull requests are required, force pushes and deletions are disabled,
conversation resolution is required, and the `Typecheck & Unit Tests` and `plumber` checks must
pass. Direct pushes to `main` are blocked for non-admins; use a branch + PR. Plumber's
branch-protection check now passes.

`test.yml` runs only on pull requests, not pushes to `main`. Security and Plumber run on pushes to
`main`.

## 8. Multi-agent operating rules

1. Read `AGENTS.md` and `PLAND.md` before starting.
2. Never push to `upstream`; push only to `origin` (`Pigna099/nextcloud-calendar-custom`).
3. Keep `main` stable. `main` is protected and requires a pull request; do app work on feature
   branches from `main`; keep planning/documentation updates on `planning` unless the owner
   directs otherwise.
4. Never force-push or rewrite shared history. Do not delete release tags.
5. Preserve GPL-3.0 licensing, upstream attribution, and commit authorship.
6. Do not change app identity (display name, slug, bundle IDs, package ID, EAS project/owner)
   without an explicit owner decision.
7. Do not commit secrets, credentials, keystores, `.env` files, generated native projects, or
   build outputs.
8. Before declaring work complete: run `yarn tsc --noEmit`, the relevant Jest tests, and a real
   dev-build smoke test for UI/native changes.
9. Update `PLAND.md` after each ticket with status, validation evidence, commit/PR links, blockers,
   and handoff notes.
10. If a tool, credential, or destination is missing, record the blocker; never guess or substitute
    another account/repository.

## 9. Known pitfalls and pending decisions

- **License metadata mismatch:** `LICENSE` is GPL-3.0; `CITATION.cff` says Apache-2.0. Keep GPL-3.0
  behavior and notices. Do not relicense without approval.
- **Upstream app identity:** `app.config.ts` still uses `com.soluce.nextcloud-calendar`,
  `com.soluce.nextcloudcalendar`, Expo owner `soluce`, and the upstream EAS project ID. Custom
  store builds will collide with the upstream app listing until new IDs, signing credentials, and
  an EAS project are chosen.
- **Upstream links:** README badges, store links, and some docs point to SoluceTechnologies. This is
  intentional attribution until a rebranding decision.
- **Generated native code:** `android/` and `ios/` are regenerated by prebuild. Only the Android
  manifest is tracked. `just e2e-build` runs `expo prebuild --clean`.
- **E2E credentials are fixtures:** passwords in `e2e/nextcloud.ts` and `e2e/*.e2e.ts` are
  disposable test values, not production secrets.
- **Large media:** `.github/assets` is roughly 70 MB, so clones are heavier than the source size.
- **Upstream branches:** only `main` and release tags were mirrored. Other upstream branches
  (`dev`, feature branches, `poc/super-calendar`) remain available through the fetch-only
  `upstream` remote and are not published in the custom repository.
- **No linter/formatter:** rely on `tsc`, tests, and review.
- **Expo SDK dependency drift:** `expo-doctor` currently reports a Hermes V1 regression
  (RN 0.86.0), 27 outdated packages, and a major `react-native-webview` mismatch. See
  `PLAND.md` T1.8 before changing native dependencies or release builds.
